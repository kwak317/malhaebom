이번 변경

- Skill에서 행동(action)과 실제 확인 결과(outcome)를 각각 추출하도록 했다. 수치 없는 관찰 결과도 보존하고, 결과가 없는 원문에서 성공을 만들어 넣지 않도록 했다.
- 행동의 수정 대상도 원문 범위만 사용하도록 했다. 테스트 실행을 테스트 코드 수정으로 바꾸지 않는다. 중간 시험에서 이 의미 차이를 발견해 최종 후보에 보완했다.
- 단순 감사·범위 안내·거절은 서버 고정 문구로 표시한다. 복합 감사 질문의 답변과 상태·행동 필드는 그대로 검증한다.
- 일반 답변에 붙은 조건부 대화 초대는 안내 문구만 제거해 실제 답변을 보존한다. 직무를 묻는 진짜 정보 질문을 무조건 삭제하지 않는다.
- JSON 파싱·구조 스키마·출력 한도 초과에만 같은 입력으로 한 번 추가 생성한다. 초안·동의·출처·허용 행동 오류와 전송 오류를 재시도로 저장에 통과시키지 않는다. 모델 호출 전에 DB나 진행 상태를 변경하지 않는다.
- 모델의 첫 원본 응답과 재시도 원본을 attempts에 모두 기록했다. 서버 문구를 반영한 성공을 모델 자체의 성공으로 세지 않았다.

시험 증거

서버 정책·복구 테스트 30개가 통과했다. 이번 최종 실행에서 서버 고정 안내는 18턴, 선택적 안내 문구 제거는 0턴 적용됐다.

실제 내용 검토

33개 경험 초안의 추출 값과 인용을 검토했다. 최종 S03의 세 반복에서 원문에 없는 테스트 코드 수정 표현은 발견되지 않았다. 다만 거절 응답 3턴에서 원본 모델의 follow_up_question에 불필요한 질문·안내문이 남아 있었다. 기존 채점은 이 필드의 질문 필요성과 의문문 여부를 모두 검사하지 않아 자동 통과로 집계했다. 서버 고정 문구가 해당 질문을 null로 제거했다. 이 내용을 자동 점수와 별도로 review-notes.json에 기록했다.

검증 한계

같은 합성 대화에서 얻은 결과다. 새로운 발화·복합 의도·긴 대화에서도 같은 품질인지 별도 평가가 필요하다. 원문 인용의 연속 일치 검사만으로 의미가 모두 검증되는 것은 아니다. 실제 응답 표를 함께 검토해야 한다.
준비 대화 제품 API·실제 DB·인증·STT·녹음/WAV 화면·후속 코칭 연결은 이번에도 검증하지 않았다. 저장과 초안은 시험 메모리만 사용했다. 운영 API·운영 DB·Langfuse에 접근하거나 배포하지 않았다. 지정된 배포 기준 소스에서 만든 후보를 로컬 컨테이너의 SDK로 호출했다.
이전 v2와 이번 v3는 첫 응답 채점 함수와 시나리오가 같지만, 서버 표시 문구가 다음 대화 기록에 들어가는 점과 저장 승인에 실제 정책 모듈만 사용하는 점이 다르다. 이번 비교는 전체 후보 흐름의 비교이며 Skill 하나의 독립적 효과 실험이 아니다.
