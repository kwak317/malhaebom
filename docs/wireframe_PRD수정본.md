# 말해봄 프론트엔드 와이어프레임 PRD 수정본

이 문서는 기존 `docs/wireframe_완성본.md`를 참고해 PRD와 충돌한 범위만 정렬한 수정본이다. 기존 문서는 보존하며, 이 문서가 PRD 기준 화면 범위와 상태의 수정 제안이다.

## 0. PRD 기준 MVP 흐름

```text
질문 선택 또는 직접 질문
→ 마이크 확인
→ 질문 음성 준비/재생
→ 5~60초 답변 녹음
→ 로그인 확인 및 비공개 저장
→ STT·VAD 전달력 분석
→ 1차 결과
→ 다음 연습에서 바꿔볼 점
→ 답변에 더해볼 내용
→ 말하기 예시
→ 검수 완료 사전 생성 코치 WAV 재생(있는 경우)
→ 동일 질문 재녹음
→ 1차/2차 비교
```

기존 UX 중 다음은 유지한다.

- 첫 화면 왼쪽 서비스 설명 영역 고정
- 오른쪽 질문 선택 → 마이크 확인 → 질문 음성 준비/재생 → 연습 시작
- 녹음 준비/중/일시정지/완료는 같은 녹음 페이지 상태 전환
- 분석 중, 1차 결과, 동일 질문 재녹음, 2차 결과·비교
- 연습 기록, 개별 삭제, 전체 삭제, 빈 상태, 오류 상태

## 1. 공통 세션 상태

```text
PracticeSession

- questionType: preset | custom | null

```

## 2. 첫 화면: 질문 선택

왼쪽 `이용안내` 영역은 기존처럼 고정한다. 오른쪽에는 `기본 질문`과 `직접 질문`을 구분해 제공한다. 정확한 시각 디자인은 별도 디자인 가이드에서 결정한다.

```text
어떤 질문으로 시작할까요?

[ 기본 질문 ] [ 직접 질문 ]
```

### preset

- 기본 질문 10개 중 하나를 선택한다.
- `questionType=preset`과 `questionId`를 저장한다.
- 직접 질문 입력값은 동시에 선택하지 않는다.

### custom

- 사용자가 직접 질문을 입력한다.
- `questionType=custom`과 `customQuestionText`를 저장한다.
- 최소 1자, 최대 200자만 등록한다.
- 공백만 입력: `질문을 입력해 주세요.`
- 200자 초과: `질문은 200자 이내로 입력해 주세요.`
- 질문 타입을 전환하면 이전 타입의 선택값을 초기화한다.

질문 미선택 또는 유효하지 않은 직접 질문에서는 메인 CTA를 비활성화한다. 유효한 질문 하나가 선택된 경우에만 `[이 질문으로 시작하기]`를 활성화한다.

유효한 기본 질문 또는 직접 질문은 답변 녹음 전에 질문 음성을 준비하고 재생한다.

- **기본 질문:** `RecordingPage`가 검수된 `/api/preset-questions/{questionId}/audio` WAV를 재생한다.
- **직접 질문:** 로그인 세션으로 `/api/questions/tts/stream`을 호출하고 실제 스트림의 시작·완료·오류를 화면 상태에 반영한다. 초기 준비 표시는 짧은 UI 타이머지만 재생 완료를 대신하지 않는다.

## 3. 마이크 확인

질문 선택 후 같은 첫 화면에서 마이크 상태를 확인한다. 왼쪽 안내 영역과 선택 질문은 유지한다.

```text
질문 선택
→ [이 질문으로 시작하기]
→ [마이크 확인]
→ 확인 중
→ 마이크 준비 완료
→ 질문 음성 준비/재생
→ [연습 시작하기]
```

마이크 확인은 실제 권한 상태에 따라 오류를 표시하며, 오류 상태는 기존 와이어프레임 정의를 재사용한다.

질문 음성 준비/재생은 별도 페이지를 추가하지 않고 기존 녹음 준비 화면 안의 상태로 제공할 수 있다.

```text
질문 음성 준비 중
→ 질문 음성 재생 중
→ [바로 녹음 시작하기]
→ 답변 녹음
```

질문 음성 재생이 끝나거나 사용자가 시작 동작을 하면 답변 녹음으로 이동한다. 질문 음성 생성 또는 재생에 실패하면 현재 화면에서 `[다시 시도]`를 제공한다.

## 4. 녹음 페이지

선택한 질문은 모든 상태에서 고정한다. `ready | recording | paused | completed`는 별도 페이지가 아니라 같은 페이지의 상태다.

- 최소 5초, 최대 60초
- 5초 미만 완료 시 분석 요청을 진행하지 않고 재녹음을 안내
- 최대 60초 도달 시 자동 완료
- 녹음 파일은 로그인 확인 전까지 제품용 저장·분석 Job 생성에 사용하지 않는다.
- WAV 파일 업로드를 지원한다. `.wav` 확장자 또는 WAV MIME 타입만 허용한다.
- WAV 업로드는 1차·2차 녹음 준비 화면 모두에서 사용할 수 있다.

### ready

질문 음성 상태는 답변 녹음 준비 화면 안에서 함께 표시할 수 있다.

- `preparing`: 질문 음성 생성/준비 중 로딩 표시
- `ready`: 질문 음성 재생 전 상태와 `[질문 다시 듣기]` 표시
- `playing`: 질문 음성 재생 중 상태 표시
- `error`: 질문 음성 생성 또는 재생 실패와 `[다시 시도]` 표시

`준비되셨다면 편하게 시작해 주세요.`

`답변은 5초 이상, 최대 60초까지 녹음할 수 있어요.`

`완벽하게 말하려 하지 않아도 괜찮아요. 평소처럼 자연스럽게 답해 주세요.`

`[녹음 시작하기]`

`[WAV 파일 업로드]`

`이미 녹음한 WAV 파일로도 분석할 수 있어요.`

### recording

- 음성 파형 또는 녹음 시각화
- 현재 시간 / `01:00`
- `[그만하기]` `[일시정지]`

### paused

`잠시 멈춰 있어요. 준비되면 이어서 말씀해 주세요.`

`[그만하기]` `[이어서 녹음하기]`

### completed

- 총 녹음 시간
- 다시 듣기
- `[다시 녹음]` `[분석하기]`

WAV 업로드 완료 상태에서는 업로드한 파일을 재생하고 `[다시 녹음]` `[분석하기]`를 표시한다. 업로드 파일에는 일반 녹음처럼 총 녹음 시간을 표시하지 않는다.

## 5. 분석 요청 전 로그인 확인

녹음 완료 후 `[분석하기]`를 누르면 먼저 로그인 상태를 확인한다. 현재 프론트는 Supabase Auth 기반 Google OAuth 로그인을 사용하며, Supabase URL과 publishable key 환경값이 설정되어야 한다.

### authenticated

```text
로그인 확인
→ Google 로그인 세션 access token 확인
→ `Authorization: Bearer <access token>`으로 분석 Job 생성
→ 분석 중
```

### unauthenticated

음성 저장과 분석 Job 생성을 하지 않는다.

```text
분석 결과를 확인하려면 로그인이 필요해요.

[ Google로 계속하기 ]
```

로그인 후에는 새 분석 요청을 시작하며, 비로그인 상태에서 임시 음성이나 Job을 먼저 생성하지 않는다.

## 6. 분석 중

중앙 정렬 화면에서 다음을 표시한다.

```text
말하기 습관을 확인하고 있어요.
잠시만 기다려 주세요.
```

개발용 Job 상태와 제품용 상태 계약은 `docs/specs/frontend-analysis-api-spec.md`에서 구분한다.

**현재 구현됨:** 로그인 세션의 access token으로 `POST /analysis-jobs`를 호출한다. 요청 본문은 `multipart/form-data`이며 `audio` 필드에 녹음 Blob 또는 업로드 WAV 파일을 전달한다. 반환된 `job_id`로 `GET /analysis-jobs/{job_id}`를 약 1초 간격으로 polling한다.

- `completed`: 결과 화면으로 이동
- `failed`: 오류 안내 후 재녹음 흐름 제공

## 7. 1차 분석 결과

공통 표시:

- 선택한 질문
- 내 답변(STT 전사문)
- 전달력 지표: 말하기 속도, 긴 침묵, 반복 표현
- 각 지표는 `나의 결과`와 `참고 기준`을 세로 막대 그래프로 비교한다.
- 그래프 안에서 `나의 결과`와 `참고 기준`을 함께 표시하며, 그래프 아래에 비교 설명을 반복하지 않는다.
- 참고 기준은 다음과 같다.
  - 말하기 속도: `320 CPM`
  - 긴 침묵: `2.48회/분`
  - 반복 표현: `0.41회/100어절`
- 표시·계산 기준은 다음과 같다.
  - 말하기 속도: Backend가 제공한 CPM 값을 표시한다.
  - 긴 침묵: 실제 분석 결과의 `answer_duration_sec`를 사용해 `긴 침묵 횟수 / answer_duration_sec × 60`으로 회/분을 계산한다.
  - 반복 표현: `반복 표현 횟수 / 전사문 공백 기준 어절 수 × 100`으로 회/100어절을 계산한다.

### 참고 기준 현재 구현 상태

- **mock 결과:** `320 CPM / 2.48회/분 / 0.41회/100어절` 참고 기준값이 적용되어 있다.
- **ResultPage:** `answerDurationSec`가 유효하면 긴 침묵을 회/분으로 계산한다. 값이 없으면 임의의 답변 시간을 만들지 않고 참고 기준을 `비교 불가`로 표시한다.
- **실제 API 결과 경로:** `AnalysisPage`가 `delivery.metrics.answer_duration_sec`를 `AnalysisResult.answerDurationSec`로 전달하고 참고 기준 `320 / 2.48 / 0.41`을 적용한다.

현재 결과 화면의 정보 구조는 다음과 같다.

```text
내 답변 전사문
분석 결과
- 말하기 속도
- 긴 침묵
- 반복 표현
다음 연습에서 바꿔볼 점
답변에 더해볼 내용
말하기 예시
[재녹음 하기]
```

### 다음 연습에서 바꿔볼 점

개선이 필요한 전달 방식만 우선순위에 따라 최대 2개 표시한다. 개선 필요 항목이 1개면 카드 1개만 표시하고, 2개 이상이면 우선순위가 높은 2개까지만 표시한다.

각 피드백 카드는 다음 구조를 사용한다.

```text
다음 연습에서 바꿔볼 점

[ 피드백 카드 ]
측정 결과
연습 목표
```

그래프의 상세 해석은 이 영역에서 제공하며, 3개 지표를 항상 모두 피드백 카드로 표시하지 않는다.

**현재 구현 상태:** `ResultPage`는 `result.feedback`을 최대 2개까지 카드로 표시한다. `feedback`이 빈 배열이면 오류 대신 현재 기준에서 우선 바꿀 전달 방식이 없다는 정상 상태 메시지를 표시한다.

### 분석 피드백 데이터 계약

결과 화면의 `AnalysisResult.feedback`은 다음 객체 배열 형식을 기대한다.

```ts
{
  title: string;
  measurement: string;
  nextPractice: string;
}
```

- **mock/ResultPage 기대 형식:** `{ title, measurement, nextPractice }[]`
- **현재 실제 API 연결부:** `AnalysisPage`는 Backend의 `delivery.feedback`에서 제목, 측정 근거, 다음 행동을 `{ title, measurement, nextPractice }`로 변환해 최대 2개 전달한다.

### 답변에 더해볼 내용

하나의 카드로 표시한다. 선택한 질문과 STT 전사문을 바탕으로 기존 답변에 추가하면 좋은 내용을 안내해 사용자가 답변을 더 구체적으로 만들 수 있도록 방향을 제시한다.

**현재 구현 상태:**

- custom 질문은 분석 응답의 `content_feedback.feedback`을 `result.contentFeedback`으로 받아 결과 화면에서 사용한다.
- preset 기본 질문은 `MOCK_CONTENT_FEEDBACK_BY_QUESTION`에 해당 질문의 mock 값이 있으면 그 값을 우선 표시하고, mock 값이 없을 때만 `result.contentFeedback`을 사용한다.
- 따라서 기본 질문에서는 Backend의 `content_feedback.feedback`이 항상 그대로 표시되는 상태는 아니다.

**추가 정리 필요:** 기본 질문에서도 실제 Backend `content_feedback.feedback`을 우선 사용할지, 현재 mock 우선 처리를 유지할지 정책과 구현을 정리해야 한다.

**별도 구현·검증 영역:** 실제 품질 분석·생성 로직, 데이터 저장 정책과 검증은 Backend/LLM 및 데이터 정책 범위에서 별도로 확정한다.

```text
답변에 더해볼 내용
선택한 질문과 내 답변을 바탕으로 추가하면 좋은 내용을 안내해요.
말하는 방식과 답변 내용을 함께 살펴봐요.
```

## 8. 말하기 예시

질문 음성은 연습 시작 전에 면접 질문을 읽어주는 기능이고, 이 절의 코치 음성은 분석 결과 후 피드백과 말하기 예시를 듣는 별도 기능이다. 사용자 답변이나 사용자 STT 전사문을 피드백용 TTS 입력으로 사용하지 않는다. 고정 템플릿은 검수 완료된 사전 생성 코치 WAV만 재생하고, 분석 LLM이 만든 승인 피드백은 [분석 결과 코치 피드백 TTS Spec](specs/coach-feedback-tts.md)에 따라 실시간 스트리밍 재생할 수 있다.

```text
CoachAudioState
- available
- generating
- unavailable
- unreviewed
```

- `available`: `코치 음성 예시 듣기`와 `[▶ 재생]`/`[■ 멈춤]`을 표시한다.
- `generating`: 텍스트 피드백을 먼저 표시하고 스트리밍 첫 음성 조각을 기다린다. 정상 완료 후에는 같은 기록에서 다시 재생할 수 있다.
- `unavailable` 또는 `unreviewed`: 플레이어를 표시하지 않고 다음 텍스트 피드백만 표시한다.

`이번 피드백은 텍스트로 확인해 주세요.`

고정 템플릿 WAV가 없거나 미검수이고 분석 LLM 기반 코치 TTS도 시작·완료되지 않으면 텍스트 안내만 표시한다. 코치 TTS의 생성·재생·만료·재시도는 [별도 Spec](specs/coach-feedback-tts.md)을 따른다.

## 9. 재녹음 준비

기존 흐름을 유지한다.

```text
질문 고정
→ 다음 연습에서 바꿔볼 점 확인
→ 답변에 더해볼 내용 확인
→ 말하기 예시
→ 재녹음 안내
→ 코치 음성 다시 듣기(검수 완료 WAV 또는 만료 전 생성 WAV가 있는 경우)
→ [재녹음 시작하기]
```

코치 WAV가 없거나 미검수이고 생성 코치 TTS도 사용할 수 없으면 텍스트 피드백만 유지한다. 이 경우에도 재녹음은 막지 않는다.

## 10. 2차 녹음·분석·비교

- 1차와 동일한 질문을 유지한다.
- 1차 녹음 페이지 UI와 상태를 재사용한다.
- `attemptNo=2`로 분석 요청한다.
- 분석 중 UI를 재사용한다.
- 2차 결과에는 새로운 피드백이나 코치 음성을 추가하지 않는다.
- 1차/2차 결과와 변화 상세를 표시한다.
- `달라진 점 확인하기`는 접기/펼치기를 유지하되 모든 변화를 무조건 개선으로 판단하지 않는다.

## 11. 연습 기록

기존 기록 UI를 유지한다.

- 기록 목록
- 질문 클릭 → 결과 조회
- 개별 삭제
- 전체 삭제
- 빈 상태
- 최대 24시간 안내

현재 상세 화면은 다음 구조를 유지한다.

```text
1차 답변
2차 답변(있는 경우)
1차 분석 결과
2차 분석 결과(있는 경우)
달라진 점
```

- 결과 화면의 세로 막대 그래프는 기록 상세에 반복하지 않는다.
- `답변에 더해볼 내용`도 기록 상세에 반복하지 않는다.
- **현재 구현됨:** 로그인 세션으로 실제 History API 목록·상세·개별 삭제·전체 삭제를 호출하고 응답을 화면 모델로 변환한다.

데이터 흐름:

- 로그인 사용자 기준으로 저장·조회한다.
- Storage는 비공개로 유지한다.
- 사용자 삭제 시 관련 세션 데이터를 삭제한다.
- 생성 후 최대 24시간 뒤 자동 삭제한다.
- 브라우저 `sessionStorage`만을 기록의 원본 저장소로 정의하지 않는다.

## 12. 주요 오류 상태

- 마이크 권한 오류
- 녹음 시작 오류
- 5초 미만 녹음
- 질문 음성 입력 검증 실패(빈 문자열·공백만 입력·300자 초과·지원하지 않는 문자/제어 문자)
- 질문 음성 생성 실패
- 질문 음성 파일 없음 또는 만료
- 질문 음성 재생 실패
- 인증 실패
- 직접 질문 검증 실패
- 음성 파일 검증 실패
- WAV 파일 형식 또는 업로드 실패
- STT 실패
- 분석 실패
- Job timeout
- 기록 조회 실패
- 개별 삭제 실패
- 전체 삭제 실패

오류는 현재 화면 안에서 표시하고, 구체적인 API code/status/UX 연결은 API Spec의 오류 계약을 따른다.
