# PRD — 채용공고 근거 기반 면접 답변 코칭 서비스

## 문제와 사용자

지방에서 혼자 신입 백엔드 면접을 준비하는 취업준비생은 자신의 프로젝트 경험을 말한 뒤에도 선택한 채용공고와 어떤 부분이 연결되는지, 본인의 행동·판단 이유·결과 확인에서 무엇이 빠졌는지 확인하기 어렵다. 범용 챗봇에 전사문을 직접 붙여 넣으면 공고에 없는 조건이나 답변에 없는 역할·성과가 보완 문장처럼 생성될 수 있고, 어떤 답변 문장을 근거로 판정했는지 추적하기도 어렵다.

말해봄은 기존 녹음·STT·VAD·전달력 피드백 흐름을 유지하면서, 사용자가 확인한 답변과 서버에 고정된 채용공고 요구사항을 근거로 내용 코칭을 제공한다. 같은 질문에 다시 답한 결과는 각 답변을 독립적으로 판정한 뒤 비교한다.

## MVP 목표

- 사용자는 기본 질문을 선택하고 5~60초 길이의 답변을 녹음한다.
- 서비스는 STT 전사문과 전달력 지표를 만들고, 사용자가 코칭에 사용할 답변 버전을 확인한다.
- 서버는 질문 ID, 확인된 답변 revision ID, 공고 snapshot ID를 이용해 코칭 문맥을 조회한다.
- 고정 Skill은 신입 백엔드 문제 해결 경험의 활성 기준만 적용하며, 문서 조각 검색이나 벡터 DB를 사용하지 않는다.
- MCP 도구는 질문, 현재 답변, 선택 공고 요구사항을 서버 레코드에서 조회한다.
- LLM은 공고 관련성, 질문 의도, 기준별 판정과 근거, 확인 질문 최대 1개, 다음 행동 최대 2개를 구조화해 제안한다.
- 서버는 Pydantic 형식 검증과 ID·인용·행동 대상 검증을 통과한 결과만 사용자에게 반환한다.
- 사용자는 같은 공고와 질문에 다시 답하고, 두 답변의 판정과 전달력 수치를 서버 규칙으로 비교한다.

## 현재 thin slice 범위

모델 선정 전에는 다음 네 단계를 먼저 완성한다.

1. 이 PRD와 코칭 범위를 고정 Skill·MCP·비RAG 방향으로 통일한다.
2. `question_id`, `answer_revision_id`, `job_snapshot_id`만 받는 코칭 입력 계약을 확정한다.
3. `POST /api/agent`가 서버 보유 mock 문맥과 고정 출력을 이용해 Pydantic 검증 결과를 반환한다.
4. FastMCP에 질문·현재 답변·공고 문맥 조회 도구를 만들고 허용 ID·소유자·만료를 검사한다.

Mock 레코드는 API와 MCP 연결을 검증하기 위한 서버 소유 개발 자료다. 운영 데이터나 실제 채용공고로 표시하지 않는다. 이후 같은 저장소 인터페이스를 Supabase의 `answer_revisions`, `job_snapshots`, `session_job_context` 구현으로 교체한다.
Mock 응답은 `COACHING_MOCK_ENABLED=true`인 개발 환경에서만 활성화하며 기본값과 배포 환경에서는 비활성화한다.

## 성공 기준

- 인증된 사용자의 올바른 세 ID로 `POST /api/agent`를 호출하면 합의한 8개 코칭 필드가 반환된다.
- 브라우저 요청으로 사용자 ID, 모델 ID, 시스템 프롬프트, 도구 이름, 공고·답변 원문을 변경할 수 없다.
- 다른 사용자 기록, 만료 기록, 허용되지 않은 ID와 서로 다른 세션의 레코드는 코칭 전에 차단된다.
- `met`과 `partial`의 모든 근거 인용은 지정된 현재 답변 문장에 정확히 존재한다.
- 활성 기준과 선택 공고 요구사항 ID의 중복·누락 또는 임의 ID가 최종 응답에 포함되지 않는다.
- 범위 밖 요청과 최종 생성 실패는 근거 없는 임시 피드백 대신 `unsupported` 또는 `unavailable`로 반환한다.
- Docker 환경에서 `/health`, `/docs`, Mock 코칭 API와 MCP 도구 검증 테스트를 재현할 수 있다.

실제 모델을 연결한 뒤에는 같은 평가셋으로 후보 모델 2개 이상을 비교하고, 계약 준수율·근거 적절성·비용·p50/p95·실패율을 기록한다. 아직 측정하지 않은 수치는 성과로 주장하지 않는다.

## API와 데이터 경계

### 사용자 API

`POST /api/agent`의 현재 action은 `analyze`만 지원한다.

```json
{
  "action": "analyze",
  "question_id": "preset-04",
  "answer_revision_id": "00000000-0000-0000-0000-000000000101",
  "job_snapshot_id": "00000000-0000-0000-0000-000000000201"
}
```

- 사용자 ID는 검증된 Bearer JWT에서 가져온다.
- 질문·답변·공고 원문과 선택 요구사항은 서버 조회 결과만 사용한다.
- 다른 사용자·만료 기록은 존재 여부가 드러나지 않는 동일한 `404` 오류로 처리한다.
- 연결된 질문이나 연습 세션이 서로 다르면 LLM 호출 전에 `409`로 차단한다.

### MCP 읽기 도구

- `get_question`: 고정 질문 본문, 질문 유형, 활성 기준과 기준 버전을 반환한다.
- `get_practice_attempt`: 사용자가 확인한 현재 답변 문장, 전달력 지표와 만료 시각을 반환한다.
- `get_job_context`: 세션에 고정된 공고 snapshot과 검토된 선택 요구사항을 반환한다.

MCP는 서버가 발급한 짧은 유효기간의 내부 토큰에 포함된 사용자와 허용 ID만 조회한다. 토큰과 사용자 ID는 모델이 생성하거나 선택하지 않는다. 임의 SQL, 임의 URL, 유사 문서 검색 도구는 제공하지 않는다.

## Skill과 판단 경계

- 전체 `skills/interview-coach/SKILL.md`, 질문 유형 문서와 `criteria.json`을 고정 버전으로 사용한다.
- 현재 답변 판정에는 현재 답변만 사용한다. 확인 응답과 과거 답변을 현재 답변에 있었던 근거처럼 섞지 않는다.
- “답변에서 확인되지 않음”과 “실제로 하지 않음”을 구분한다.
- 사용자가 말하지 않은 역할·행동·기술·이유·수치·성과를 만들지 않는다.
- 사투리·억양을 내용 감점 근거로 쓰지 않는다. 전사 오류 가능성은 `undetermined`로 처리한다.
- 공고 관련성을 전체 직무 역량이나 합격 가능성으로 확대하지 않는다.

## 현재 제약 기준

현재 프로젝트의 범위·금지 사항·팀 자율 제약은 [CONSTRAINTS](CONSTRAINTS.md)를 기준으로 확인합니다. 아래는 현재 코칭 구현의 경계입니다.

- 면접 합격 가능성, 인성, 경험의 진실성 또는 실제 역량 향상을 자동 판정하지 않는다.
- RAG, 임베딩, 벡터 DB, 과거 우수 답변 검색을 사용하지 않는다.
- 모델 선정 전 단계에서 실제 LLM 품질·비용·지연 성과를 주장하지 않는다.
- 공고 탐색·추천·원문 수집·요구사항 분석·기업 조사·공급자 및 직무·질문 유형 확장의 제품 범위는 [TARGET_STATE](TARGET_STATE.md)를 따른다. 원천 채용 API의 자동 수집·갱신을 제품 범위에서 일괄 제외하지 않는다.
- 코칭에는 서버의 원문·인용 검증을 통과한 공고 요구사항만 사용하며, 검증되지 않은 검색 결과를 자동으로 사용하거나 공고에 없는 조건을 생성하지 않는다.
- 외부 면접관 검토, 사용자 파일럿, 개선의 인과 효과가 완료됐다고 표시하지 않는다.
- 립싱크·아바타·이미지 생성, 사용자 음성 Voice Cloning을 포함하지 않는다.

## 데이터·안전

- 원본 음성, 전사문, 확인 응답과 코칭 결과는 비공개로 관리한다.
- 운영 연습 기록은 기존 24시간 보관 정책을 따르며 revision과 코칭 문맥도 원래 기록의 만료 시각을 넘겨 연장하지 않는다.
- 음성·답변을 모델 학습이나 Voice Cloning 데이터로 사용하지 않는다.
- 연구·평가용 장기 보관은 운영 기록에서 자동 복사하지 않고 별도 동의·목적·종료일·철회 절차를 마련한 경우에만 수행한다.
- 서버 비밀키와 MCP 내부 토큰은 브라우저 응답, 모델 입력, 일반 로그와 Git에 기록하지 않는다.
