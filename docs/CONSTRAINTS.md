# Constraints

> 제공 기획 기반 운영 문서. 기능·기술·정책은 목표 또는 재사용 계획이며 현재 구현 완료를 뜻하지 않는다. 기존 1차 코드는 이관되었으며 정적 조사 결과는 [CURRENT_STATE](CURRENT_STATE.md)를 따른다. 실행 검증은 별도다.

## 공식 조건과 팀 자율 제약의 경계

공식 과제 조건의 canonical은 [REQUIREMENTS](REQUIREMENTS.md)다. RAG·LangGraph 금지는 공식 조건이다. 아래 벡터 DB·임베딩 검색 제외, 신입 백엔드/문제 해결 경험 한 유형, 확인 질문·행동 수 제한, 장기 누적 코칭 제외 등은 팀이 더 좁힌 자율 제약이다. 공식적으로 허용된 기술이라도 팀 범위에 자동 추가하지 않는다.

## Scope Constraints

- 대상 사용자는 신입 백엔드 개발자 준비생으로 제한한다.
- 초기 기준 검증은 프로젝트 문제 해결 경험에 집중한다. 2026-09-28 사용자 요청으로 화면의 기본 질문 1~10번은 각 질문의 고정 루브릭으로 코칭한다 ([Spec](specs/all-preset-question-coaching.md)).
- 추가 기본 질문의 규칙은 팀 초안이며, 문제 해결 평가 결과를 다른 질문의 품질 증거로 확대하지 않는다.
- 한 세션은 검토된 공고 1개와 관련 요구사항 1~2개만 사용한다.
- 장기 누적 코칭을 현재 범위로 가정하지 않는다.

## Explicitly Out of Scope

- RAG / LangGraph: 공식 금지 조건 준수 (상세 판정 기준은 REQUIREMENTS 참조)
- 벡터 DB
- 문서 조각/임베딩 검색
- 실시간 웹 검색 기반 면접 팁 수집
- 채용 적합성 판정
- 모든 기술 면접 정답 판정
- 합격 가능성 예측
- 지원자 전체 역량/채용 적합성 판정
- 경험·성과 대필
- 사용자가 말하지 않은 경험·성과를 채운 자동 모범답안 전체 작성
- 코칭 예시를 여러 개 만들거나 합격 답안·정답으로 표시하는 기능
- 새로운 STT/TTS 학습의 MVP/제품 범위 편입 (별도 승인된 재현 가능 실험은 아래 예외 규칙 적용)
- 무제한 대화형 에이전트
- 실시간 전문가 상담 플랫폼

## Coaching Constraints

- 확인 질문은 최대 1개다.
- 다음 행동은 내용·전달력을 합쳐 최대 2개다.
- 확정 답변과 현재 코칭만 재구성한 2~3문장 예시는 결과당 1개만 허용한다.
- 확인되지 않은 정보는 추정하지 않고 `[실제로 확인한 방법]`처럼 표시한다.
- 예시는 정답·합격 답안·사실 검증 결과로 표시하지 않는다.
- 사용자가 말하지 않은 역할·수치·성과·기술을 만들지 않는다.
- 답변에 없는 것과 실제로 하지 않은 것을 구분한다.
- 특정 키워드 등장만으로 기준 충족을 판정하지 않는다.
- 수치가 없다는 이유만으로 자동 부족 판정하지 않는다.
- 정성적 검증도 구체적인 조건과 결과가 있으면 인정할 수 있다.
- 사투리·억양을 내용 평가 감점 근거로 쓰지 않는다.
- STT 오류 가능성이 있으면 확인을 우선한다.

## Job Context Constraints

- 공고 관련 경험이 있다는 사실을 전체 직무 역량 충족으로 확대하지 않는다.
- NCS를 기업의 실제 채점표로 간주하지 않는다.
- 공고에 없는 조건을 NCS/직무 정의에서 가져와 필수조건처럼 추가하지 않는다.
- 공고 조회 실패/상세 누락을 가상 조건으로 채우지 않는다.

## Comparison Constraints

- 1차/2차 비교는 같은 사용자·연습 세션·공고·질문·기준의 호환 가능한 결과만 허용한다.
- `undetermined`가 있으면 개선/퇴보로 단순 순위화하지 않는다.
- 답변이 길어졌다는 이유만으로 개선으로 판정하지 않는다.
- 설명 보완을 실제 역량 향상이나 합격 가능성 향상으로 표현하지 않는다.

## Data Constraints

- 연구용 사례별 정답을 운영 LLM 입력에 넣지 않는다.
- 운영 기록과 연구용 사례를 분리한다.
- 실제 사용자 사례를 자동으로 공개 Dataset/저장소에 복제하지 않는다.
- 동의 범위를 넘겨 외부 모델/관측 서비스에 전송하지 않는다.

## Evaluation Constraints

공식 요약은 생성 모델과 judge 분리를 권장하지만 팀은 기존 `evals/README.md` 및 `EVAL_REPORT.md`의 더 엄격한 분리 규칙을 유지한다. LLM-as-judge 사용 시 생성 모델과 판정 모델을 다르게 둔다. 공식 평가 조건 자체는 [REQUIREMENTS](REQUIREMENTS.md)를 따른다.

## 실험 규칙과 현재 범위

[실험 재현 규칙](experiments/README.md)은 별도로 승인된 실험의 수행 조건이다. STT/TTS 신규 학습은 여전히 MVP/제품 범위에서 제외하지만, 2026-09-19 사용자 승인으로 기존 LoRA adapter weight 유실에 대응하는 Whisper Medium STT retrain을 별도 실험으로 허용한다. 이 실험은 [STT retrain Spec](specs/stt-finetuning-retrain.md)을 따르며 기존 CT2 모델을 baseline으로 보존하고, 고정 holdout 평가 전에는 제품 기본 모델을 교체하지 않는다. TTS 신규 학습은 이번 예외에 포함되지 않는다.

## 비교 후 면접 대화 범위 확장

사용자 요청으로 1·2차 비교 뒤 해당 연습 세션의 텍스트 면접 대화만 허용한다. 고정 턴 수 제한은 없지만 매 응답 꼬리질문은 최대 1개이며, 사용자가 종료하면 요약한다. 기존 분석의 확인 질문/다음 행동 제한, 근거 없는 경험 생성 금지와 원래 기록 불변 규칙은 유지한다. 장기 저장·RAG·재채점·음성 대화는 제외한다.
