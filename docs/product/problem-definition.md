## 1. 2주 MVP에서 검증하지 않을 범위

이번 MVP는 검토된 채용공고 1건과 신입 백엔드의 문제 해결 질문 1개 유형에서, 첫 답변의 누락을 근거와 함께 찾고 재답변의 변화를 확인하는 데 집중한다.

아래 범위는 가치가 없어서가 아니라, 현재 문제 가설과 다른 제품·데이터·운영 역량을 요구하므로 이번 MVP에서는 검증하지 않는다.

| 이번 MVP에서 검증하지 않을 범위 | 제외 이유 |
|---|---|
| 장기 커리어 메모리, 자동 개인화, 미검토 공고 자동 반영 | 경험·공고 정보의 정확성, 동의, 수정·삭제, 잘못된 기억의 정정 체계가 먼저 필요하다. |
| 실제 면접 중 실시간 답변 보조 또는 답변 대필 | 사용자가 스스로 답변을 보완하는지 검증하는 목표와 다르고, 면접 공정성과 오남용 위험도 커진다. |
| 아바타·립싱크·Voice Cloning·신규 STT/TTS 모델 학습 | 핵심 가설과 직접 관련이 적고, 2주 안에 품질·비용·동의 문제까지 검증하기 어렵다. |
| 기술 답변의 정답 판정, 지원자의 역량·성격·합격 가능성 평가 | 타당도 검증과 전문 평가 데이터가 필요한 고위험 판단이다. 말해봄은 답변에서 드러난 설명의 충분성만 다룬다. |

### 변경 불가 운영 원칙

다음은 “하지 않을 일”이 아니라 서비스의 안전성과 신뢰를 위한 운영 원칙이다.

- 사용자가 말하지 않은 역할·행동·기술·수치·성과를 사실처럼 생성하지 않는다.
- `답변에서 확인되지 않음`과 `실제로 하지 않음`을 구분한다.
- 검토 완료된 공고 snapshot만 코칭 문맥으로 사용한다.
- 공고와 답변의 연결 근거가 없으면 억지로 연결하지 않고 `연결 근거 없음`으로 남긴다.
- 답변 원문과 인용이 일치하지 않거나 구조화 출력 계약 검증에 실패하면, 추정 피드백 대신 `unavailable`을 반환한다.
- 고정된 Skill과 서버가 검증한 현재 문맥·구조화 계약을 사용하며 RAG·LangGraph는 사용하지 않는다.

### 이번 MVP에서 반드시 해야 하는 것

| 우선순위 | 해야 하는 일 | 완료 기준 |
|---|---|---|
| P0 | 검토된 공고·질문·판단 기준을 고정한다. | 어떤 공고 요구사항, 질문, `criterion_id`, Skill 버전으로 분석했는지 재현할 수 있다. |
| P0 | 첫 답변 전사문을 사용자가 확인한다. | 사용자가 확인하거나 수정한 전사문만 분석에 사용한다. |
| P0 | 답변을 질문별 활성 기준으로 분석한다. | C/R/A/D/V 전체를 일괄 요구하지 않고, 해당 질문의 활성 `criterion_id`만 `met`·`partial`·`not_observed`·`undetermined`로 분류한다. |
| P0 | 모든 판단에 답변 원문 근거를 붙인다. | `met`·`partial` 판단에는 현재 답변의 정확한 인용이 포함된다. |
| P0 | 다음 연습 행동을 제안한다. | 해석이 필요한 경우에만 확인 질문은 최대 1개, 다음 답변 행동은 최대 2개만 제안한다. |
| P0 | 같은 질문에 재답변하도록 돕는다. | 첫 답변과 재답변을 독립적으로 분석하고, 같은 기준의 설명 변화만 비교한다. |
| P0 | 결과를 검증 가능하게 남긴다. | 인용 불일치, 구조화 출력 실패, 재시도, 비용, 응답 시간, 실패율을 기록한다. |
| P1 | 말하기 전달력 지표를 보조 정보로 제공한다. | 말속도·침묵·반복 등은 제공할 수 있으나, 내용 근거 기반 코칭보다 앞세우지 않는다. |

## 2. 한 문장 문제 정의

신입 백엔드 취업준비생은 자신의 프로젝트 문제 해결 경험을 면접 답변으로 말한 뒤에도, **지원 공고와 질문 의도에 비추어 본인의 행동·판단 이유·결과 확인 중 무엇이 빠졌는지 근거를 가지고 판단하고 다음 답변에 구체적으로 보완하기 어렵다.**

## 3. 사용자

### 핵심 사용자

- 프로젝트 경험은 있지만 이를 면접 답변으로 구조화하는 데 익숙하지 않은 신입 백엔드 취업준비생
- 지원할 채용공고는 정했지만, 자신의 경험을 공고의 요구사항과 연결해 설명하기 어려운 사람
- 면접관이나 현직자에게 반복적으로 첨삭받기 어려워 혼자 녹음·재연습하는 사람

## 4. 상황

사용자는 지원 공고를 선택하고 “프로젝트 개발 중 발생한 문제를 어떻게 해결했나요?”와 같은 질문에 답한다. 그러나 혼자 답변을 다시 들어보거나 범용 챗봇에 전사문을 입력하는 방식만으로는 다음을 확인하기 어렵다.

- 질문에서 활성화된 문제 상황·원인 판단·본인 행동·선택 이유·결과 확인 기준이 충분히 드러났는가?
- 답변의 어느 문장을 근거로 충분하거나 부족하다고 판단했는가?
- 공고와 관련된 경험을 말했는가, 아니면 공고에 없는 조건을 억지로 끼워 넣었는가?
- 추상적인 “더 구체적으로 말하세요”가 아니라 다음 답변에서 실제로 무엇을 보완해야 하는가?
- 재답변이 단순히 길어진 것인지, 빠졌던 설명이 실제로 추가된 것인지?

이 문제로 인해 사용자는 같은 답변을 반복해도 개선 방향을 정하기 어렵고, 근거가 불분명하거나 자신의 실제 경험과 다른 피드백을 그대로 연습할 위험이 있다.

## 5. 핵심 작업

> 사용자가 지원 공고에 맞춰 실제 프로젝트 경험을 설명한 뒤, 답변에서 확인된 근거와 빠진 정보를 구분하고, 다음 연습에서 보완할 행동을 결정해 같은 질문에 다시 답할 수 있도록 한다.

| 단계 | 사용자가 해야 할 일 | 말해봄이 지원할 일 |
|---|---|---|
| 준비 | 검토된 채용공고와 연습 질문을 선택한다. | 공고의 선택 요구사항과 질문별 판단 기준을 고정한다. |
| 첫 답변 | 자신의 실제 경험만으로 답변하고 전사문을 확인한다. | 확인된 답변 문장에서 판단 근거를 찾고 누락된 설명을 구분한다. |
| 보완 결정 | 추가로 설명할 내용을 정한다. | 확인 질문은 최대 1개, 다음 연습 행동은 최대 2개로 제안한다. |
| 재답변 | 같은 공고·질문에 다시 답한다. | 두 답변을 독립적으로 판정한 뒤 같은 기준에서 추가·유지·악화·판단불가를 비교한다. |

## 6. LLM과 코드 역할 분리

| 업무 | LLM이 판단할 일 | 코드·서버가 결정할 일 |
|---|---|---|
| 코칭 문맥 준비 | 원문이나 ID를 임의로 선택하지 않는다. | 로그인 사용자, 허용된 질문·답변 revision·검토된 공고 snapshot을 조회하고 소유권·만료·연결 관계를 검사한다. |
| 질문·공고 해석 | 질문 의도와 제공된 공고 요구사항의 관련성을 해석한다. | 적용할 질문, Skill 버전, 공고 요구사항 ID와 원문을 고정한다. |
| 답변 분석 | 질문에 연결된 활성 기준만 `met`·`partial`·`not_observed`·`undetermined`로 분류하고 근거 문장을 제안한다. | 활성 기준의 누락·중복, 허용되지 않은 상태값, 인용 원문 일치, 기준 ID를 검사한다. |
| 코칭 생성 | 부족한 설명, 확인 질문 최대 1개, 다음 행동 최대 2개를 제안한다. | 개수·형식·범위 제한을 검증하고 실패 시 재시도 또는 `unavailable`을 반환한다. |
| 재답변 비교 | 첫 답변과 재답변을 각각 독립적으로 분석한다. | 같은 `criterion_id`의 상태와 근거를 비교해 변화 결과를 계산하며, 비교만을 위한 세 번째 LLM 호출은 하지 않는다. |
| 음성·운영 처리 | STT·VAD·TTS, 권한, 저장·삭제, 비용 계산을 판단하지 않는다. | 녹음·전사·전달력 지표·TTS, 보관·삭제, 로그·비용·지연시간 측정과 오류 처리를 수행한다. |

## 7. 성공 기준

아래 수치는 구현 완료 사실이 아니라, 사용자 조사와 평가 전에 확정할 초기 검증 목표다.

| 구분 | 성공 기준 | 확인 방법 |
|---|---|---|
| 문제 적합성 | 초기 대상자 3~5명 중 3명 이상이 최근 면접 준비에서 같은 어려움을 구체적 사례로 설명한다. | 반구조화 인터뷰와 최근 사용한 대안 기록 |
| 행동 가능성 | 사용자의 80% 이상이 코칭 후 추가 설명 없이 가장 먼저 보완할 내용과 다음 행동을 각각 1개 이상 말할 수 있다. | 코칭 직후 과업 질문과 관찰 |
| 근거성 | `met`·`partial` 판정의 인용은 확인된 현재 답변 원문과 100% 일치한다. | 30건 이상 평가셋의 자동 인용 검사 |
| 공고 연결성 | 공고 요구사항과 답변의 연결은 원문 근거를 가지며, 근거 없는 연결을 사람 검토자가 발견하지 않는다. | 공고-답변 연결 사례의 사람 검토 |
| 안전성 | 답변에 없는 역할·행동·기술·수치·성과를 사실처럼 생성하는 치명적 오류가 0건이다. | 실패 유도 사례와 사람 검토 |
| 출력 안정성 | 구조화 출력 계약 준수율 95% 이상을 100회 이상 반복 실행에서 달성한다. | 동일 조건 반복 평가와 실패 유형 기록 |
| 개선 확인 | 재답변에서 보완된 항목을 원문 근거로 제시하고, 사람 검토자가 변화 방향에 동의한다. | 동일 질문의 첫 답변·재답변 사례별 검토 |
| 운영 가능성 | 후보 모델별 비용, 실패율, p50/p95 응답 시간을 같은 조건에서 측정하고 선택 근거를 남긴다. | 모델 비교 리포트와 실행 로그 |

## 8. 판단 경계

- 성공은 **답변에서 빠진 설명을 찾고 보완 행동을 정할 수 있게 되는 것**이지, 면접 합격이나 실제 역량 향상을 보장하는 것이 아니다.
- 재답변의 변화는 기록하되, 전후 차이만으로 코칭의 인과 효과가 입증됐다고 주장하지 않는다.
- 사용자가 말하지 않은 경험은 만들지 않으며, “답변에서 확인되지 않음”과 “실제로 하지 않음”을 구분한다.
- 코칭에는 검토된 공고만 사용하고, 원천 검색 결과를 검토 없이 자동 반영하지 않는다.
- 전달력 지표는 보조 정보이며, 답변 내용의 충분성이나 실제 역량을 단독으로 판정하지 않는다.

## 10. 차별화 가설

“AI 면접관”, “공고 맞춤 질문”, “꼬리질문”, “피드백”은 이미 제공되는 기능이다. 말해봄은 다음 세 가지를 함께 제공하는 좁은 흐름으로 차별화한다.

1. **검토된 공고 요구사항 ↔ 질문 의도 ↔ 답변 원문**의 연결을 사용자가 직접 확인할 수 있다.
2. “더 구체적으로 말하세요”가 아니라, **어느 기준의 설명이 답변에서 관찰되지 않았는지**를 구분한다.
3. 재답변이 길어졌는지가 아니라, **이전 답변에서 빠졌던 설명이 실제로 추가됐는지**를 같은 기준으로 확인한다.

> **차별화 가설:** 사용자는 공고 맞춤 질문이나 종합 점수보다, 자신의 현재 답변 원문에서 판단 근거와 누락 항목을 확인하고 동일 질문의 재답변에서 그 누락이 보완됐는지를 보는 흐름에서 더 명확한 다음 행동을 정할 수 있다.

## 최종 목표

사용자가 코칭을 읽은 뒤 **“내 답변의 어떤 표현이 근거였고, 무엇이 답변에서 확인되지 않았으며, 다음 답변에서 무엇을 바꿔야 하는지”를 스스로 설명하고 실제 재답변에 반영할 수 있는 상태**를 만든다.
