# Project Overview

> 제공 기획 기반 운영 문서. 기능·기술·정책은 목표 또는 재사용 계획이며 현재 구현 완료를 뜻하지 않는다. 기존 1차 코드는 이관되었으며 정적 조사 결과는 [CURRENT_STATE](CURRENT_STATE.md)를 따른다. 실행 검증은 별도다.

## 한 줄 정의

말해봄은 **지원 공고와 실제 프로젝트 경험을 연결하고, 답변에서 확인되는 근거와 빠진 설명을 짚은 뒤 같은 질문에 다시 답하며 보완 여부를 비교하는 신입 백엔드 면접 코치**다.

## 해결하려는 문제

신입 백엔드 준비생은 프로젝트 문제 해결 경험을 설명할 때 다음을 스스로 확인하기 어렵다.

- 질문 의도에 맞는 설명을 했는가
- 팀 행동과 본인의 행동을 구분했는가
- 원인 판단과 방법 선택의 근거를 설명했는가
- 결과를 실제로 어떻게 확인했는가
- 첫 답변의 누락이 두 번째 답변에서 실제로 보완됐는가

## 초기 사용자

- 설명할 프로젝트 경험이 있는 신입 백엔드 개발자 준비생
- 면접 피드백 기회가 부족한 사람
- 지역 조건은 가설이며 핵심 조건으로 확정하지 않는다.

## MVP 범위

초기 MVP는 **프로젝트 문제 해결 경험** 한 유형에 집중한다.

2026-09-28 사용자 요청으로 화면의 기본 질문 1~10번에 질문별 코칭을 연결한다. 문제 해결 기준은 4번에 유지하며, 추가 질문의 기준은 팀 초안이다. 질문별 모델 품질 검증과 구현 연결은 구분한다 ([Spec](specs/all-preset-question-coaching.md)).

대표 질문:

> 프로젝트 개발 중 발생한 문제를 어떻게 해결했나요?

세션에서는 검토된 채용공고 1개와 관련 요구사항 1~2개를 선택하고 같은 공고·질문·기준으로 1차와 2차 답변을 비교한다.

## 사용자 흐름

1. 공고 1개와 관련 요구사항 1~2개 선택
2. 문제 해결 질문 선택 또는 지원 범위 안에서 직접 입력
3. 5~60초 답변 녹음
4. STT 결과 확인·수정
5. 구조화된 내용 코칭 확인
6. 필요한 경우 확인 질문 1개에 짧게 응답
7. 다음 연습 행동 최대 2개 중 선택
8. 같은 질문에 두 번째 답변
9. 같은 기준으로 전후 변화 비교

## 사용자에게 보여줄 핵심 결과

1. 답변에서 확인한 근거
2. 부족하거나 판단하기 어려운 항목
3. 확인 질문 최대 1개
4. 다음 연습 행동 최대 2개
5. 선택 공고 요구사항과 현재 답변의 관련성
6. 1차/2차 답변에서 실제로 추가·미보완된 설명

## 핵심 자체 데이터 후보

말해봄이 직접 생성·검토하려는 핵심 기록은 다음 네 가지다.

- 사용자의 실제 역할
- 설명에서 빠진 정보
- 코칭 이후 변화
- 그 변화에 대한 사람의 판단

이 데이터가 있다는 이유만으로 독점성이나 품질 우위를 주장하지 않는다. 출처·버전·검토 상태와 실제 비교 결과를 함께 남긴다.

## 차별화가 아니라 검증할 가치

공고 기반 질문, AI 모의면접, 꼬리질문, 피드백, 반복 연습 자체는 이미 기존 서비스에 존재한다. 따라서 말해봄은 기능 존재가 아니라 다음을 검증한다.

- 공고 요구와 답변 근거를 정확히 연결하는가
- 답변에 없는 것과 실제로 하지 않은 것을 구분하는가
- 재답변의 변화가 사람의 판단과 일치하는가
