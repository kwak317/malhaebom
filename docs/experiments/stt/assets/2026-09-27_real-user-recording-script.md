# 말해봄 STT 실사용 평가 녹음 대본

## 녹음 방법
각 항목을 별도 음성 파일로 녹음한다. 문장을 읽을 때는 지나치게 또박또박 읽기보다 실제 면접에서 답변하듯 자연스럽게 말한다. 괄호 안의 추임새도 그대로 발화한다.

---

### 01. 자기소개
안녕하세요. 저는 컴퓨터공학을 전공하면서 모바일 애플리케이션 개발과 인공지능 프로젝트를 경험했습니다. 최근에는 백엔드 개발과 음성 인공지능 분야에도 관심을 가지고 공부하고 있습니다.

### 02. 지원 동기
제가 이 직무에 지원한 이유는 제가 경험한 소프트웨어 개발 역량을 실제 사용자에게 도움이 되는 서비스로 연결하고 싶었기 때문입니다. 특히 문제의 원인을 직접 분석하고 해결하는 과정에서 흥미를 느낍니다.

### 03. 프로젝트 설명
대학교에서 시각장애인을 위한 코딩 교육 애플리케이션을 개발한 경험이 있습니다. 카메라로 블록을 인식하고, 인식된 결과를 음성과 진동을 통해 사용자에게 전달하도록 구현했습니다.

### 04. 성능 개선 경험
초기 모델에서는 이미지 한 장을 처리하는 데 약 9.1초가 걸렸습니다. 이후 모델 실행 방식과 후처리 과정을 개선해서 약 5.4초까지 처리 시간을 단축했습니다.

### 05. 문제 해결 경험
개발 과정에서 예상한 결과와 실제 출력이 다르게 나오는 문제가 있었습니다. 처음에는 모델 자체의 문제라고 생각했지만, 로그를 확인해 보니 후처리 과정에서 좌표 변환이 잘못되고 있었습니다.

### 06. 협업 경험
팀 프로젝트에서는 Git과 GitHub를 사용해서 코드를 관리했습니다. 기능별로 브랜치를 나누고 Pull Request를 통해 코드 리뷰를 진행했으며, 충돌이 발생한 경우에는 변경 이유를 확인한 뒤 병합했습니다.

### 07. 갈등 해결
팀원과 구현 방향에 대한 의견이 달랐던 적이 있습니다. 각자의 방법을 바로 선택하기보다는 요구사항과 구현 비용을 비교했고, 간단한 프로토타입을 만들어 결과를 확인한 뒤 방향을 결정했습니다.

### 08. 실패 경험
한 프로젝트에서는 모델의 검증 정확도는 괜찮았지만 실제 거래 비용까지 반영하자 최종 결과가 좋지 않았습니다. 이 경험을 통해 모델의 정확도만으로 서비스의 성능을 판단하면 안 된다는 것을 배웠습니다.

### 09. 장점
제 장점은 문제가 발생했을 때 단순히 임시 해결책을 적용하기보다 원인을 확인하려고 한다는 점입니다. 로그와 실행 환경을 확인하고, 재현 조건을 줄여 가면서 문제를 찾는 편입니다.

### 10. 단점
반대로 문제를 깊게 파고들다 보면 하나의 문제에 시간을 많이 사용하는 경우가 있습니다. 그래서 최근에는 먼저 해결해야 하는 문제와 나중에 개선해도 되는 문제를 구분하려고 노력하고 있습니다.

---

### 11. 기술 질문 — 운영체제
프로세스와 스레드의 가장 큰 차이는 자원 공유 방식이라고 생각합니다. 프로세스는 기본적으로 독립적인 메모리 공간을 사용하지만, 같은 프로세스의 스레드는 코드와 힙 등의 자원을 공유합니다.

### 12. 기술 질문 — 네트워크
TCP는 연결 지향적인 프로토콜이며 패킷의 순서와 전달 여부를 확인합니다. 반면 UDP는 이러한 과정을 줄여서 비교적 빠르게 데이터를 전달할 수 있습니다.

### 13. 기술 질문 — 데이터베이스
데이터베이스 인덱스는 검색 속도를 높이기 위해 사용하는 자료구조입니다. 다만 인덱스가 많아지면 저장 공간을 더 사용하고 삽입이나 수정 작업의 비용이 증가할 수 있습니다.

### 14. 기술 질문 — REST API
REST API를 설계할 때는 리소스를 중심으로 URL을 구성하고 HTTP 메서드의 의미를 일관되게 사용하는 것이 중요하다고 생각합니다. 예를 들어 조회에는 GET, 생성에는 POST를 사용할 수 있습니다.

### 15. 기술 질문 — Docker
Docker를 사용하면 애플리케이션과 필요한 실행 환경을 컨테이너 단위로 관리할 수 있습니다. 덕분에 개발 환경과 배포 환경의 차이를 줄이는 데 도움이 됩니다.

### 16. 기술 질문 — 머신러닝
머신러닝 모델을 평가할 때 학습 데이터의 정확도만 보는 것은 위험합니다. 학습에 사용하지 않은 validation set과 test set을 분리해서 일반화 성능을 확인해야 합니다.

### 17. 기술 질문 — STT
음성 인식 시스템을 평가할 때는 CER과 WER 같은 지표를 사용할 수 있습니다. CER은 문자 단위 오류율이고 WER은 단어 단위 오류율이기 때문에 한국어에서는 두 지표를 함께 보는 것이 좋다고 생각합니다.

### 18. 기술 질문 — LLM
대규모 언어 모델을 서비스에 사용할 때는 단순한 응답 품질뿐 아니라 지연 시간, 비용, 출력 형식의 안정성도 함께 고려해야 합니다.

---

### 19. 숫자 포함 문장
실험에는 총 1,233개의 음성 샘플을 사용했고 CER은 2.5876퍼센트, WER은 9.7740퍼센트로 측정되었습니다.

### 20. 날짜와 시간
2026년 9월 23일 오전 10시 30분에 테스트를 시작했고 약 1시간 20분 동안 결과를 확인했습니다.

### 21. 영어 기술용어
이번 프로젝트에서는 Python, FastAPI, React, PostgreSQL, Docker, GitHub Actions를 사용했고 모델 추론에는 Whisper Medium과 CTranslate2를 사용했습니다.

### 22. 영어와 한국어 혼합
프런트엔드에서 API request를 보내면 backend server가 access token을 확인하고, 정상적인 경우 JSON response를 반환하도록 구현했습니다.

### 23. 버전 및 단위
개발 환경에서는 Python 3.11과 CUDA 12.8을 사용했고 GPU 메모리는 최대 약 16기가바이트까지 사용할 수 있습니다.

### 24. URL과 약어
CI와 CD 파이프라인을 구성하고 PR이 생성되면 자동으로 테스트가 실행되도록 했습니다. API와 DB 연결 상태도 health check를 통해 확인했습니다.

---

### 25. 자연스러운 추임새
음, 제가 가장 어려웠던 부분은 처음에 어디서 문제가 발생했는지 알 수 없었다는 점입니다. 그래서 어, 일단 로그를 하나씩 확인하면서 오류가 발생하는 위치를 좁혀 갔습니다.

### 26. 문장 수정
제가 프로젝트에서 맡았던 역할은 백엔드 개발이었고, 아니 정확히 말하면 백엔드뿐만 아니라 모델 테스트와 문서 정리도 같이 담당했습니다.

### 27. 반복 표현
처음에는 모델을 바로 교체하려고 했는데, 모델을 바로 교체하기보다는 기존 모델과 새 모델을 같은 조건에서 비교하는 것이 먼저라고 판단했습니다.

### 28. 긴 답변
프로젝트를 진행하면서 가장 중요하다고 느낀 점은 개발자가 생각하는 좋은 기능과 실제 사용자가 필요로 하는 기능이 항상 같지는 않다는 점이었습니다. 그래서 기능을 구현하기 전에 사용자 입장에서 어떤 문제가 있는지를 먼저 정의하고, 구현한 이후에도 실제 사용 과정에서 불편한 부분이 없는지 확인하려고 했습니다.

### 29. 긴 기술 답변
STT 모델을 파인튜닝한 뒤에는 단순히 학습 loss가 감소했다는 이유만으로 모델이 좋아졌다고 판단하지 않았습니다. 기존 모델과 후보 모델을 동일한 테스트 데이터와 동일한 decoding 조건에서 실행하고 CER과 WER을 비교했으며, 새로운 데이터에 적응하면서 기존 데이터의 성능이 떨어지는 catastrophic forgetting도 함께 확인했습니다.

### 30. 실제 면접형 답변
제가 입사하게 된다면 처음부터 모든 시스템을 바꾸려고 하기보다는 기존 코드와 서비스 구조를 먼저 이해하겠습니다. 이후 반복적으로 발생하는 문제나 개선 효과가 큰 부분을 찾고, 작은 단위로 수정하면서 테스트와 코드 리뷰를 통해 안정적으로 개선해 나가고 싶습니다.
