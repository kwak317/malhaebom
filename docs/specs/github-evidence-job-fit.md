# GitHub 기술 증거 기반 공고 핏 진단

> 상태: 제안 Spec. 이 문서는 기능 목표와 경계를 정한 것이며, 현재 구현 완료를 뜻하지 않는다.

## Why

- **페르소나**: 자신의 프로젝트는 있지만, 신입 백엔드 공고의 기술 요구를 면접 답변으로 어떻게 증명해야 할지 모르는 취업 준비생.
- **상황**: 사용자는 프로젝트에서 라이브러리와 도구를 사용했어도, 답변에서 기술 이름만 나열하거나 선택 이유·트레이드오프·검증 방법을 설명하지 못한다.
- **문제**:
  1. 공고의 요구와 저장소에서 확인되는 기술 근거 사이의 간극을 사용자가 파악하기 어렵다.
  2. 일반적인 기술 꼬리질문은 사용자의 실제 프로젝트와 무관한 지식 퀴즈가 되기 쉽다.
  3. 저장소의 코드 존재를 사용자의 기여·경험으로 오인하거나, 저장소에 없는 경험을 없다고 단정할 위험이 있다.
- **측정 지표 (구현 전 기준선 필요)**:
  - 사람이 검토한 표본에서 `근거 확인`/`설명 보완 필요`/`저장소 기준 미확인` 분류의 정확도
  - 2차 답변에서 `설명 보완 필요` 항목 중 실제로 선택 근거 또는 검증 방법이 추가된 비율
  - 사용자가 근거 카드의 기여 범위를 확인한 비율

## Goal

- **해결 목표**: **선택한 공고의 요구사항과 이 프로젝트에서 확인되는 기술 근거 사이에 어떤 간극이 있는지**를 대조하고, 답변에서 설명할 수 있는 기술 근거와 보완할 설명을 제시한다. 여기서 프로젝트 근거는 사용자가 제출·확인한 공개 GitHub 저장소의 허용 범위로 제한한다.
- **성공 기준**:
  1. 결과의 모든 기술 근거는 허용 파일 또는 사용자가 고른 PR·커밋에서 추적 가능하다.
  2. 저장소에서 찾지 못한 기술을 `경험 없음`으로 표현하지 않고 `저장소 기준 미확인`으로만 표시한다.
  3. 심층 꼬리질문은 확인된 기술 근거와 사용자의 답변에서 언급한 내용에만 연결한다.
  4. 내용·전달력 다음 행동은 기존 정책대로 합계 최대 2개, 확인 질문은 최대 1개다.
- **Out of Scope**:
  - 합격 가능성, 전체 직무 역량, 채용 적합성 또는 공고 외 일반 취업 유리 기술의 판정
  - private 저장소 OAuth 연동, 임의 URL fetch, 임의 코드 실행
  - 전체 저장소 청킹·임베딩·검색(RAG) 및 GitHub 전체 이력 분석
  - 저장소 코드만으로 사용자의 작성·기여 사실을 자동 확정하는 기능
  - 공고에 없는 기술을 필수 조건으로 추가하거나, 없는 경험을 대필하는 기능

## What

### Happy Path

1. 사용자는 검토된 공고 1개와 요구사항 1~2개를 선택하고, 공개 GitHub 저장소 URL을 입력한다.
2. 서버는 GitHub URL·공개 상태·크기·허용 파일을 검증하고, README와 선언형 의존성·배포 설정 파일, 사용자가 고른 PR 또는 커밋 1~3개에서 기술 근거 후보를 추출한다.
3. 사용자는 후보 중 자신이 면접에서 설명할 수 있는 기여 범위를 선택해 `프로젝트 근거 카드`로 확정한다.
4. 서버는 각 선택 공고 요구사항을 `근거 확인`, `설명 보완 필요`, `저장소 기준 미확인` 중 하나로 표시하고, 원문 파일/PR/커밋 링크와 함께 이유를 제시한다.
5. 사용자가 답변을 녹음·확정하면, 기존 코칭은 답변에서 언급한 기술과 확정 근거 카드가 만나는 지점만 이용해 선택 이유·트레이드오프·검증 방법의 설명 보완을 제안한다.
6. 필요한 경우 심층 꼬리질문 1개를 제시하고, 2차 답변에서는 같은 근거 카드·공고 요구사항으로 설명 보완 여부를 비교한다.

### 결과 상태 정의

| 상태 | 의미 | 금지 표현 |
| --- | --- | --- |
| `evidence_confirmed` | 선택한 공고 요구와 연결할 수 있는, 사용자가 확인한 저장소 근거가 있다. | 이 근거만으로 해당 역량 보유·합격 가능을 단정 |
| `explanation_needed` | 기술 또는 설정 근거는 있으나, 답변에서 선택 이유·본인 행동·검증 중 필요한 설명이 없다. | 기술 사용 자체가 부족하다고 단정 |
| `not_confirmed_in_repository` | 선택한 범위의 저장소 근거에서 해당 요구를 확인하지 못했다. | 경험이 없거나 부적합하다고 단정 |

### Edge Cases

| # | 상황 | 처리 방식 |
| --- | --- | --- |
| EC-01 | GitHub URL이 아니거나 공개 저장소가 아님 | 입력을 거부하고, 공개 GitHub 저장소 URL만 지원한다고 안내한다. |
| EC-02 | 저장소가 너무 크거나 허용 파일을 찾지 못함 | 분석하지 않고 제한 사유를 표시한다. 사용자는 README 또는 허용 PR·커밋을 다시 선택할 수 있다. |
| EC-03 | 의존성 선언만 있고 실제 사용 근거를 확인할 수 없음 | `선언만 확인`으로 별도 표시하며 실제 사용·기여로 승격하지 않는다. |
| EC-04 | 공고 요구가 저장소에는 없지만 사용자가 관련 경험을 주장함 | `저장소 기준 미확인`을 유지한다. 기존 답변 코칭의 확인 질문으로 설명을 받을 수 있으나, 원래 답변 근거로 소급하지 않는다. |
| EC-05 | 답변에서 저장소·근거 카드에 없는 기술을 언급함 | 해당 기술의 사실성·숙련도를 추정하지 않는다. 필요한 경우 최대 1개의 중립 확인 질문을 사용한다. |
| EC-06 | 선택 PR·커밋에 민감값 또는 개인정보가 있음 | 원문을 코칭/관측 서비스로 전송하지 않고, 민감 패턴 탐지 시 분석을 중단하고 사용자에게 안내한다. |
| EC-07 | 공고 요구가 모호하거나 기술명만 있음 | 공고 원문을 인용하고, 필수 기술로 확장 해석하지 않는다. |

## How

### 입력과 보안 경계

- 입력은 `github.com/{owner}/{repo}` 형식의 공개 저장소 URL만 허용한다. redirect URL, 다른 호스트, 임의 파일 URL은 허용하지 않는다.
- 서버는 GitHub API 또는 검증된 GitHub 콘텐츠 endpoint만 사용한다. 코드 실행·임의 shell command·임의 SQL 도구를 제공하지 않는다.
- 초기 허용 파일은 README, `package.json`, lockfile을 제외한 의존성 선언 파일, `requirements*.txt`, `pyproject.toml`, Dockerfile/Compose, CI 설정 및 사용자가 명시적으로 선택한 PR·커밋 메타데이터로 제한한다. 정확한 크기·파일 수 상한은 구현 Spec에서 결정한다.
- GitHub 원문 전체를 LLM에 전달하지 않는다. 서버가 파일 경로·기술명·선언/사용 판정·공개 링크를 포함한 구조화된 근거 후보를 만든 뒤, 사용자가 확정한 최소 정보만 코칭 입력에 포함한다. 이는 RAG가 아니다.
- 답변, 사용자 확인, 저장소 원문은 기존 비공개·만료·Langfuse redaction 정책을 따른다. 공개 저장소여도 원문을 운영 로그나 연구 Dataset에 복제하지 않는다.

### 데이터 모델 초안

```text
RepositorySource
- id, user_id, github_owner, github_repo, default_branch, fetched_at, expires_at

RepositoryEvidenceCandidate
- id, repository_source_id, technology_name, evidence_kind
  (readme | dependency_declaration | deployment_config | selected_pull_request | selected_commit)
- source_url, source_path, excerpt_hash, usage_status (declared | confirmed_by_user)

ProjectEvidenceCard
- id, user_id, repository_evidence_candidate_id, user_confirmed_scope,
  confirmation_at

JobEvidenceGapAssessment
- id, practice_session_id, requirement_id, status,
  evidence_card_ids, rationale, created_at
```

- `user_confirmed_scope`는 사용자가 설명 가능한 기여를 직접 서술 또는 선택한 값이다. 자동 추론한 기여도를 저장하지 않는다.
- 기존 `practice_session`, 답변 revision, 코칭 run의 소유자·유효기간·호환성 검사를 재사용한다.

### 코칭 계약 확장

- 기존 `job_alignment`에는 requirement별 GitHub 근거 상태와 근거 ID만 추가한다. 상태 의미는 기존 `met` 등 답변 평가 상태와 혼동하지 않도록 별도 enum을 쓴다.
- 심층 꼬리질문은 `ProjectEvidenceCard`가 최소 하나이고 답변이 그 기술·문제를 언급할 때만 생성한다.
- 다음 행동은 공고의 선택 요구와 연결된 설명 보완으로 제한한다. 예: “Redis를 사용했다면 선택 이유와 만료 정책을 실제 사례로 설명해 보세요.”
- 답변과 저장소 근거가 충돌해도 서버가 사실 판정을 내리지 않는다. 근거 출처와 중립 확인 질문만 제공한다.

## AC (Given-When-Then)

**AC-01 · 공개 GitHub 저장소에서 기술 근거 후보 생성**
- GIVEN: 인증된 사용자가 허용 형식의 공개 GitHub 저장소 URL과 선택 공고 요구사항을 제출했다.
- WHEN: 서버가 허용 파일을 읽어 기술 근거를 추출한다.
- THEN: 각 후보에는 기술명, 근거 종류, 파일/PR/커밋 링크, `declared` 또는 사용자 확인 전 상태가 기록되고, 임의 URL이나 코드는 실행되지 않는다.

**AC-02 · 사용자 확인 없는 기여 단정 방지**
- GIVEN: 의존성 파일에 특정 라이브러리가 선언되어 있다.
- WHEN: 사용자가 해당 항목을 자신의 설명 가능 기여로 확인하지 않았다.
- THEN: 결과는 라이브러리의 선언 사실만 표시하며, 사용자의 사용·기여·숙련으로 표현하지 않는다.

**AC-03 · 공고 요구와 저장소 근거의 간극 표시**
- GIVEN: 선택한 공고의 요구사항이 있고, 확정된 프로젝트 근거 카드가 있다.
- WHEN: 공고 핏 진단을 실행한다.
- THEN: 각 요구사항은 `evidence_confirmed`, `explanation_needed`, `not_confirmed_in_repository` 중 하나로 표시되고, 이유와 추적 가능한 근거 링크를 포함한다.

**AC-04 · 저장소 미확인을 경험 부재로 오인하지 않음**
- GIVEN: 공고 요구사항에 대한 저장소 근거를 확인하지 못했다.
- WHEN: 진단 결과를 사용자에게 표시한다.
- THEN: “경험 없음”, “부족한 인재”, “불합격 가능성” 같은 표현 없이 `저장소 기준 미확인`과 선택 가능한 설명 보완 안내만 표시한다.

**AC-05 · 근거 연결형 심층 꼬리질문**
- GIVEN: 사용자가 확정 근거 카드와 연결된 기술을 답변에서 언급했다.
- WHEN: 기존 코칭이 확인 질문을 필요로 판단한다.
- THEN: 최대 1개의 질문은 해당 기술의 선택 이유·트레이드오프·검증 중 답변에 없는 부분만 묻고, 저장소·답변에 없는 역할·수치·성과를 가정하지 않는다.

**AC-06 · 재답변 비교의 설정 고정**
- GIVEN: 같은 공고·요구사항·근거 카드로 1차 답변과 2차 답변이 확정됐다.
- WHEN: 비교를 실행한다.
- THEN: 요구사항별 설명 보완 여부와 양쪽 답변 근거를 표시하되, 설명 보완을 전체 역량 또는 합격 가능성 향상으로 표현하지 않는다.

**AC-07 · 공개 저장소 원문 보호**
- GIVEN: 분석 대상 파일 또는 선택 PR에 secret·개인정보 패턴이 감지됐다.
- WHEN: 서버가 코칭 입력 또는 관측 로그를 구성하려 한다.
- THEN: 해당 원문을 외부 모델·Langfuse·연구 Dataset에 보내지 않고 분석을 중단하며, 사용자에게 안전한 재선택 방법을 안내한다.
